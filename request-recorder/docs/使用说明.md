# RequestRecorder 使用说明

本组件把 HTTP 请求/响应采集能力封装为标准 Maven Starter：业务工程只需引入一个依赖 + 一段 yml 配置，即可自动采集请求与响应并写入**独立的采集数据库**，业务工程无需编写任何采集代码、无需注册 Filter、也不使用业务自身的数据源。

## 一、能力概览

| 能力 | 说明 |
| --- | --- |
| 自动装配 | Boot 2 走 `spring.factories`，Boot 3 走 `AutoConfiguration.imports`，零代码接入 |
| 独立数据库 | 采集库由组件自建连接池（HikariCP，缺失时自动回退 JDBC 直连），与业务数据源完全隔离 |
| 异步写入 | 有界队列 + 可配置 worker；队列满丢弃新记录并计数，绝不阻塞业务线程 |
| 请求采集 | Method / URL / URI / Query / Path / Headers / Body / Content-Type / ClientIP / UA / 时间 / 请求唯一 ID / 项目编码与名称 |
| 响应采集 | 状态码 / Headers / Body / 响应大小 / 耗时 / 异常信息 |
| 脱敏 | Headers 与 JSON、Form 字段默认脱敏，支持自定义 |
| 防循环 | 回放请求带 `X-Request-Replay: true` 时不采集 |
| 优雅停机 | 关机时先等在途采集入库，再按超时排空队列，超时丢弃并计数 |
| 数据兼容 | 表结构与既有 Python Tkinter 回放 GUI 完全一致 |

## 二、接入步骤

### 1. 引入依赖

Spring Boot 2.x（2.7.x 及以上）：

```xml
<dependency>
    <groupId>com.requestrecorder</groupId>
    <artifactId>request-recorder-spring-boot-2-starter</artifactId>
    <version>1.0.0</version>
</dependency>
```

Spring Boot 3.x（3.0.x 及以上）：

```xml
<dependency>
    <groupId>com.requestrecorder</groupId>
    <artifactId>request-recorder-spring-boot-3-starter</artifactId>
    <version>1.0.0</version>
</dependency>
```

> 两个 Starter 不能同时引入同一个工程。Boot 2 Starter 依赖 `javax.servlet`，Boot 3 Starter 依赖 `jakarta.servlet`。

依赖需要先安装到本地仓库或私服，见《发布说明.md》。

### 2. 建库建表

执行仓库根目录的 `sql/request_recorder.sql`（MySQL 8.0）：

```bash
mysql -uroot -p < sql/request_recorder.sql
```

脚本创建数据库 `request_recorder` 与三张表：`http_request_project`、`http_request_record`、`http_replay_history`。

### 3. 配置 application.yml

```yaml
request-recorder:
  enabled: true
  project-code: order-service          # 必填，多项目隔离标识
  project-name: 订单管理系统            # 可选，GUI 显示名，缺省回落为 project-code
  database:
    jdbc-url: jdbc:mysql://127.0.0.1:3306/request_recorder?useUnicode=true&characterEncoding=UTF-8&serverTimezone=Asia/Shanghai
    username: recorder
    password: change-me
  async:
    enabled: true
    queue-capacity: 5000
    workers: 2
  max-body-size: 1048576
  exclude-paths:
    - /actuator/**
    - /favicon.ico
```

配置完成后直接启动业务工程即可，日志中会出现：

```text
RequestRecorder 配置已加载: ...
RequestRecorder 数据源已初始化: url=jdbc:mysql://127.0.0.1:3306/request_recorder?..., poolSize=3, type=HikariConnectionProvider
RequestRecorder 项目已注册: projectCode=order-service
RequestRecorder 采集过滤器已注册: urlPattern=/*
```

### 4. 验证采集

访问任意业务接口后查询数据库：

```sql
SELECT id, project_code, method, uri, response_status, duration_ms, request_time
FROM http_request_record
ORDER BY id DESC LIMIT 10;
```

## 三、接入示例（最小可运行）

```java
@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

@RestController
class DemoController {
    @GetMapping("/api/hello")
    public String hello(@RequestParam(defaultValue = "world") String name) {
        return "hello:" + name;
    }

    @PostMapping("/api/order")
    public Map<String, Object> order(@RequestBody Map<String, Object> body) {
        Map<String, Object> result = new LinkedHashMap<String, Object>();
        result.put("accepted", true);
        result.put("sku", body.get("sku"));
        return result;
    }
}
```

配套 `application.yml` 见上一节，无需其他代码。

仓库内的两个集成测试模块即为完整可运行的接入示例，遵循「不省略、可直接跑」的要求，只用测试作用域打包：

- `request-recorder-integration-tests-boot2`（Spring Boot 2.7.18 + javax.servlet）
- `request-recorder-integration-tests-boot3`（Spring Boot 3.3.0 + jakarta.servlet）

其中的 `ItApplication` 演示了正常接口、POST JSON、抛出异常、大响应、被排除路径五类端点，可直接复制为业务工程的脚手架。

## 四、多项目共用采集库

同一个采集数据库可被多个业务工程共用，靠 `project-code` 区分：

```yaml
# 工程 A
request-recorder:
  project-code: project-a
  project-name: 项目 A
```

```yaml
# 工程 B
request-recorder:
  project-code: project-b
  project-name: 项目 B
```

约束与行为：

1. `project-code` 必填，全局唯一，长度不超过 100。
2. 启动时自动向 `http_request_project` 注册：不存在则插入，已存在则更新 `project_name` 与 `description`。
3. 注册失败只会打印告警，**不会导致业务服务启动失败**。
4. 修改 `project-name` 不影响历史记录归属，因为记录按 `project_code` 关联。

## 五、与 Python 回放 GUI 配合

1. 采集库填写 GUI 的 `python/config.py` 数据库配置即可看到请求列表（按 `project_code` 分项目展示）。
2. 列表中选中记录，右侧查看请求/响应详情，右键执行回放。
3. 回放时 GUI 会自动附加：

```http
X-Request-Replay: true
X-Request-Replay-Id: 123
```

Java 侧在采集判定前检查该头，命中即跳过采集，因此**回放不会写回采集表**，不会形成回放→采集→再回放的死循环。回放结果写入 `http_replay_history`。

> 若请求经过网关/代理，需确认该自定义头能透传，否则防循环会失效。

## 七、采集机制说明

```text
HTTP 请求
   ↓
RecorderFilter（OncePerRequestFilter，urlPattern=/*）
   ↓  RequestSnapshot（ContentCachingRequestWrapper 包装）
业务 Controller / 业务 Filter
   ↓  ResponseSnapshot（自定义 BoundedResponseWrapper 限流缓存 + copyBodyToResponse）
RequestCollector：判定是否采集（排除路径 / 静态资源 / 回放头 / WebSocket / SSE）
   ↓  RecordData（含脱敏）
AsyncRecordQueue（有界队列，worker 线程池）
   ↓  重试 max-retries 次
RecorderRepository → 独立采集库（MySQL 8.0）
```

关键实现细节：

1. **请求体可被业务正常读取**：使用 `ContentCachingRequestWrapper`，业务侧读取不受影响。
2. **响应体不丢失**：`BoundedResponseWrapper` 在 `finally` 中调用 `copyBodyToResponse()`，异常路径同样保证写回。
3. **大响应不撑爆内存**：响应缓存受 `max-body-size` 限制，超出即截断并置 `response_truncated=1`。
4. **异常请求仍记录**：业务抛异常时记录状态码与 `exception_message`，不覆盖原始异常。
   - 若业务工程用 `@RestControllerAdvice` 在 Filter 链内把异常转成 500 响应（推荐），则采集到的是真实的 500 与响应体，`exception_message` 为 null——这是正常行为。
   - 若异常直接冒泡到容器 `/error`，Filter 只能看到容器重定向前的状态码，建议业务工程统一使用全局异常处理器。
5. **不适配缓存的流量**：WebSocket 握手、SSE、文件下载（`Content-Disposition: attachment`）只记录元数据或直接跳过；multipart 默认只记录元数据。

## 八、关闭与降级

- 临时关闭采集（业务不受影响）：

```yaml
request-recorder:
  enabled: false
```

- 配置缺失（未配 `project-code` 或 `database.jdbc-url`）：默认**打印错误并自动禁用采集**，业务正常启动；若希望配置错误直接阻断启动：

```yaml
request-recorder:
  fail-fast: true
```

- 采集库不可用：写入失败按 `max-retries` 重试，仍失败仅记录日志与 `failed` 计数，业务响应不受任何影响。

## 九、常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 启动日志无「配置已加载」 | `enabled=false` 或配置非法被禁用 | 检查 `enabled` 及 `project-code`、`database.jdbc-url` |
| yml 配置不生效 | 配置项层级写错（如把 `workers` 写在根级） | 按《配置说明.md》的层级书写 |
| 数据库无记录 | 表未建 / 连接失败 / 路径被排除 | 查看日志 `RequestRecorder 写入失败`；核对 `exclude-paths` |
| 记录数少于请求数 | 命中排除规则（静态资源、回放头、SSE 等）或队列满被丢弃 | 查看 `QueueStats` 的 `dropped` 计数 |
| 响应体为空 | 响应非文本类型（二进制） | 属预期：二进制只记录占位符 |
| 回放后记录数增加 | 网关未透传 `X-Request-Replay` | 配置网关允许该头透传 |
