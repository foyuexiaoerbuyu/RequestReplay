# RequestRecorder 兼容性说明

## 一、版本支持矩阵

| 组件 | 支持范围 | 已验证版本 | 备注 |
| --- | --- | --- | --- |
| Spring Boot 2.x | 2.7.x 及以上 | 2.7.18 | 依赖 `javax.servlet`（Servlet 3.1+） |
| Spring Boot 3.x | 3.0.x 及以上 | 3.3.0 | 依赖 `jakarta.servlet`（Servlet 6.0） |
| JDK | 8 / 11 / 17 / 21 | 8（core、Boot 2）、17（Boot 3） | core 与 Boot 2 Starter 字节码为 Java 8 |
| Servlet 容器 | Tomcat / Jetty / Undertow | 随 Boot 内嵌容器 | 只需要标准的 `Filter` 与 `HttpServletRequest` 缓存包装能力 |
| 数据库 | MySQL 8.0 | MySQL 8.3 驱动 / 8.0 服务端 | H2 2.1.214 仅用于集成测试 |
| 连接池 | HikariCP / 无（JDBC 直连回退） | HikariCP 4.0.3 | 业务未引入 HikariCP 时自动回退，不影响接入 |
| 序列化 | Jackson / 内置兜底 | Jackson 2.13.5 | 未引入 Jackson 时使用内置轻量 JSON 实现 |
| 日志 | SLF4J 1.7 / 2.x | 1.7.36 | 通过 SLF4J API 输出，跟随业务工程日志实现 |
| 回放 GUI | Python Tkinter 客户端 | 现有 `python/main.py` | 表结构、字段名、状态值全兼容 |

## 二、Boot 2 与 Boot 3 的差异处理

| 关注点 | Boot 2 适配模块 | Boot 3 适配模块 |
| --- | --- | --- |
| Servlet 命名空间 | `javax.servlet.*` | `jakarta.servlet.*` |
| 自动装配注册方式 | `META-INF/spring.factories` | `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` |
| 编译器 release | 8 | 17 |
| Servlet 依赖范围 | `provided` | `provided` |
| 采集逻辑 | 完全一致（共用 core） | 完全一致（共用 core） |

设计上把「与 Servlet 无关」的全部逻辑（配置、模型、队列、连接池、脱敏、仓储、采集判定）下沉到 `request-recorder-core`，把「与 Servlet 相关」的 `Filter` 与响应包装按命名空间各写一份，从而保证两套适配的行为一致、无分叉维护成本。

## 三、与既有组件的兼容性

### 1. 与旧版采集组件

- 表结构与字段名未变更，新增字段均为可选（见第三节表格），旧版 `sql` 脚本创建的表可继续使用；如缺新字段，重跑 `sql/request_recorder.sql` 中的 `ALTER`/建表语句即可。
- 采集写入语义未变，`http_request_record` 的历史数据无需迁移。

### 2. 与业务工程既有能力

| 场景 | 是否兼容 | 说明 |
| --- | --- | --- |
| 业务自定义 Filter（登录鉴权、TraceId、日志等） | 兼容 | 采集 Filter 以 `urlPattern=/*` 注册，不修改 Request/Response 语义 |
| 业务读取请求体（`@RequestBody`、`getInputStream()`） | 兼容 | 使用 `ContentCachingRequestWrapper`，业务读取不受影响 |
| 业务写入响应流 | 兼容 | 响应包装在 `finally` 中回写正文，异常路径同样保证输出 |
| 业务使用 `@RestControllerAdvice` 全局异常处理 | 推荐 | 可在 Filter 链内得到真实的 500 状态码与响应体，采集结果与回放目标一致 |
| 业务直接抛异常交由容器 `/error` | 部分兼容 | Filter 只能看到容器重定向前的状态，采集到的状态码可能与最终响应不一致；异常信息仍会记录 |
| 业务占用 `HttpServletRequest` 的 `inputStream` 后再次读取 | 兼容 | 依赖容器 `ContentCachingRequestWrapper` 的缓存语义 |
| 业务使用 SSE / WebSocket / 文件下载 | 兼容 | 默认跳过或只记录元数据，不缓存大流量正文 |
| 业务显式引入 HikariCP 且版本为 2.x/3.x | 兼容 | core 对 HikariCP 为 `optional` 依赖，使用业务提供版本；无则回退 JDBC 直连 |
| 业务同时引入 Boot 2 与 Boot 3 Starter | **不兼容** | 会出现 `javax`/`jakarta` 重复装配，必须二选一 |
| 响应式 WebFlux 工程 | **不支持** | 仅提供基于 Servlet 的采集，WebFlux 需另做 `WebFilter` 适配 |
| 业务自行配置采集库 `DataSource` | 不需要且不生效 | 组件恒用独立连接池，不与业务数据源共享 |

### 3. 与 Python 回放 GUI

| 项目 | 状态 |
| --- | --- |
| 读取 `http_request_record` 列表 | 兼容 |
| 按 `project_code` 分项目展示 | 兼容 |
| 详情（请求头、请求体、响应头、响应体） | 兼容 |
| 回放（附加 `X-Request-Replay: true`） | 兼容，Java 侧识别并跳过采集，避免回放再采集的死循环 |
| 回放结果写入 `http_replay_history` | 兼容 |
| 回放历史回查 | 兼容 |

## 四、数据表兼容细节

`http_request_record` 主要字段（与 `sql/request_recorder.sql`、`RecorderRepository` 写入语句一致）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint 自增 | 主键，Python GUI 回放时作为 `X-Request-Replay-Id` |
| `project_code` | varchar(100) | 项目隔离键 |
| `project_name` | varchar(200) | 项目显示名快照 |
| `request_id` | varchar(64) | 请求唯一 ID（业务未带 TraceId 时由组件生成） |
| `request_time` | datetime(3) | 请求时间 |
| `method` | varchar(20) | HTTP 方法 |
| `url` | text | 完整 URL |
| `uri` | varchar(1000) | 请求路径 |
| `query_params` / `path_params` | longtext | 查询参数 / 路径参数（JSON） |
| `request_headers` / `request_body` | longtext | 请求快照（已脱敏） |
| `client_ip` / `user_agent` | varchar | 客户端信息 |
| `response_status` | int | HTTP 状态码 |
| `response_headers` / `response_body` | longtext | 响应快照（已脱敏） |
| `duration_ms` | bigint | 耗时（毫秒） |
| `response_size` | bigint | 响应字节数 |
| `exception_message` | text | 业务异常信息（有全局异常处理时为 null） |
| `request_truncated` / `response_truncated` | tinyint(1) | 是否因超限被截断 |

`http_request_project` 表含 `project_code`（唯一）、`project_name`、`description`、`created_at`、`updated_at`；组件启动注册项目时，`project_name` 与 `description` 会被更新，`updated_at` 随之刷新。

写入前统一做长度控制：正文超过 `max-body-size` 即截断；`varchar` 字段写入前按列宽截断，避免因超长导致整条记录写入失败。

## 五、已知限制

1. **仅支持 Servlet 技术栈**：WebFlux / 响应式工程不支持。
2. **单个工程只能引入一个 Starter**：Boot 2 与 Boot 3 版本互斥。
3. **二进制响应只记元数据**：图片、文件流等不再缓存原文，避免垃圾数据。
4. **采集库单点**：采集库不可用时只记日志与计数，不做本地落盘补偿；如需保证不丢，可提高 `async.max-retries` 并监控 `QueueStats.failed`。
5. **不采集响应流的实时性内容**：SSE 长连接只记录请求元数据，不记录流式分片。
6. **回放防循环依赖请求头透传**：经网关/代理时需确保 `X-Request-Replay` 不被丢弃，否则回放请求会被再次采集。

## 六、升级与降级建议

- **升级 Boot 2 → Boot 3**：业务工程改用 `request-recorder-spring-boot-3-starter`，yml 配置项无需调整；确认自身已迁移到 `jakarta.servlet`。
- **降低采集开销**：缩小 `max-body-size`、关闭 `record-static-resources`、增加 `exclude-paths`、下调 `async.workers`。
- **提高吞吐**：提高 `async.queue-capacity` 与 `workers`、将采集库与业务库分离到不同实例。
- **紧急止损**：`request-recorder.enabled=false` 重启业务即可完全停采，或通过配置中心热更新后重启。
